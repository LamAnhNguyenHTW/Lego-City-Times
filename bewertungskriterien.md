# Bewertungskriterien fuer die Demo-Anwendung

Ziel der Belegarbeit ist die Entwicklung einer IT-Infrastruktur, welche verlaesslich auf hohe Auslastung und Ausfaelle reagieren kann bzw. Probleme zuverlaessig erkennt.

## Anforderungen

- [x] Eine Kurzdokumentation als `README.md`-Datei beschreibt wie Anwendung bedient wird (1 Punkt)
  - Erfuellt: Start, URLs, Beispiel-Requests, Health-Check, Persistenz, Monitoring und Lasttests sind beschrieben.
- [x] Alle notwendigen Dateien, `Dockerfiles`, Container-Images sind in der Abgabe enthalten oder in zugaenglichen Repositories (bspw. `ghcr`) verfuegbar. (1 Punkt)
  - Erfuellt: `Dockerfile`s fuer `frontend`, `content-service`, `search-service`, `docker-compose.yml`, Monitoring-Konfigurationen, Skripte und Secrets-Dateireferenzen sind im Repo enthalten. Images werden lokal gebaut.
- Die Infrastruktur kann mit `docker-compose` gestartet werden (4 Punkte)
    - [x] Wenn Schritte zur Initialisierung notwendig sind (bspw. Datenbank-Tabellen anlegen o.ae.) werden diese automatisch ausgefuehrt
      - Erfuellt: JPA `ddl-auto=update`, `DataInitializer`, Elasticsearch-Mapping/Index und Compose-Dependencies uebernehmen die Initialisierung.
    - [x] Die Webanwendung kann ueber die in der `README.md` angegebene URL aufgerufen werden.
      - Erfuellt: `https://localhost/` ueber Nginx/TLS.
    - [x] Die Webanwendung besitzt einen in der `README.md` angegebenen Endpunkt an den Daten gesendet werden (bspw. ein API-Call oder Form-Submit).
      - Erfuellt: `POST https://localhost/internal/search/articles/index` inklusive `curl`-Beispiel.
    - [x] Es existiert eine **URL** mit welcher der Health-Status der Anwendung ueberprueft werden kann.
      - Erfuellt: `https://localhost/actuator/health`.
- [x] Persistente Daten sind in Docker Volumes abgelegt und bleiben nach Neustart der Infrastruktur erhalten. (1 Punkt)
  - Erfuellt: Volumes fuer PostgreSQL, Elasticsearch, Uploads, Prometheus, Alertmanager, Grafana und Backups sind konfiguriert.
- Lasttests (12 Punkte)

          - Erfuellt laut `load-tests/results/README.md`: PASS, 0.00% Fehlerquote.
        - [x] fuer 100 parallele Anfragen (1 Sekunde Ramp-up).
          - Erfuellt laut `load-tests/results/README.md`: PASS, 0.00% Fehlerquote.
        - [x] fuer 1000 parallele Anfragen (5 Sekunden Ramp-up).
          - Erfuellt laut `load-tests/results/README.md`: PASS, 0.00% Fehlerquote.
        - [x] fuer 1000 parallele Anfragen (1 Sekunde Ramp-up).
          - Erfuellt laut App-Net-Lauf in `load-tests/results/README.md`: PASS, 0.00% Fehlerquote.
        - [x] fuer 1000 Anfragen pro Minuten ueber 10 Minuten.
          - Erfuellt laut App-Net-Lauf in `load-tests/results/README.md`: PASS, 0.00% Fehlerquote.
    - Der Daten verarbeitende Web-Endpunkt funktioniert:
        - [x] fuer 10 parallele Anfragen (0 Sekunden Ramp-up, normale Requests).

- Verfuegbarkeit (6 Punkte)
    - [x] Der Ausfall eines Webservers fuer das Frontend beeinflusst nicht die Verfuegbarkeit der Anwendung.
      - Erfuellt konzeptionell: `frontend` ist mit `deploy.replicas: 3` konfiguriert, Nginx nutzt Docker-DNS und `least_conn`.
    - [x] Der Ausfall des Backend wird im Monitoring angezeigt.
      - Erfuellt: Prometheus scrapt `content-service`/`search-service`, Alerts `ServiceDown`, `ServiceDegradedWarning` und Replica-Alerts sind konfiguriert.
    - [x] Bei Ausfall des Backend zeigt das Frontend eine passende Fehlermeldung.
      - Erfuellt: `apiFetch`, `describeApiError` und `ErrorBanner` zeigen Netzwerk-/Timeout-/Serverfehler an.
    - [x] Der Ausfall des Datenbank wird im Monitoring angezeigt.
      - Erfuellt: `postgres-exporter`, Alert `PostgreSqlDown` und `PostgresExporterDown`.
    - [x] Bei Ausfall der Datenbank zeigt das Frontend eine passende Fehlermeldung.
      - Erfuellt indirekt: Content-Service gibt bei DB-Problemen Serverfehler zurueck, Frontend meldet "moeglicherweise ist die Datenbank nicht erreichbar".
    - [ ] Bei Ueberlastung einzelner Dienste skaliert der Dienst vertikal (Scale-Out).
      - Fehlt bzw. nur statisch vorbereitet: `deploy.replicas` setzt mehrere Instanzen fuer Frontend, Content und Search, aber keine automatische Skalierung bei Ueberlastung ist konfiguriert.
- Monitoring (6 Punkte)
    - [x] Die Services besitzen Health-Checks.
      - Erfuellt: Healthchecks fuer Elasticsearch, Postgres, Content, Search, Frontend und Nginx.
    - [x] Die Services besitzen geeignete Abhaengigkeiten um eine geordnete Start-Reihenfolge sicherzustellen.
      - Erfuellt: `depends_on` mit `service_healthy` fuer zentrale Abhaengigkeiten.
    - [x] Stuerzt ein Container unerwartet ab wird dies erkannt und angezeigt.
      - Erfuellt: cAdvisor/Prometheus/Grafana plus Alerts fuer fehlende Services, Replicas und Container-Anzahl.
    - [x] Stuerzt ein Container unerwartet ab wird dieser automatisch neu gestartet.
      - Erfuellt: `restart: unless-stopped` bei den Services.
    - [x] Ueberwachungslimits fuer die Container sind konfiguriert.
      - Erfuellt: CPU-/Memory-Limits unter `deploy.resources.limits` sowie Alert-Regeln fuer CPU/Memory.
    - [x] Benachrichtigungen werden versendet bei ueberschreiten von Ueberwachungslimits.
      - Erfuellt: Alertmanager wird mit Slack Webhook aus `.env` gerendert; Alert-Regeln fuer CPU/Memory/HTTP/DB sind vorhanden.
- Security (5 Punkte)
    - [x] Dienste sind sinnvoll in verschiedenen Netzen isoliert.
      - Erfuellt: `app-net`, internes `db-net`, `monitoring-net`.
    - [x] Kommunikation mit Endpunkten erfolgt SSL-Verschluesselt (selbst-signiertes Zertifikat ist ausreichend).
      - Erfuellt: Nginx terminiert TLS auf Port 443 mit Zertifikat unter `monitoring/nginx/certs`.
    - [x] Passwoerter und sonstige Geheimnisse sind nicht in `docker inspect` sichtbar sondern mit **Docker Secrets** oder verschluesselten `.env`-Dateien umgesetzt.
      - Erfuellt fuer zentrale Secrets: Postgres-, Grafana- und JWT-Secret werden als Docker Secrets eingebunden; Slack Webhook kommt aus `.env` und wird lokal gerendert. Hinweis: `secrets/*.txt` liegen im Arbeitsbaum und sollten fuer eine echte Abgabe nicht mit echten Produktionswerten befuellt sein.
    - [x] Es sind keine unnoetigen Ports exponiert.
      - Erfuellt: nach README nur `80`, `443` und Grafana `3000`; Backend, DB, Prometheus, Alertmanager und Elasticsearch sind nicht auf Host-Ports gemappt.
    - [x] Zusaetzliche Massnahmen wie **Read Only**-Dateisysteme oder Capabilities wurden implementiert oder ausprobiert und dokumentiert.
      - Erfuellt: `read_only`, `tmpfs`, `cap_drop`, gezielte `cap_add` und `no-new-privileges` sind in Compose konfiguriert.
- Sonstiges (4 Punkte)
    - [ ] Die Infrastruktur enthaelt eine Web-Application-Firewall (WAF)
      - Fehlt: Es gibt nur Planungsnotizen zu ModSecurity/OWASP CRS in `conductor/phase-5-sonstiges.md`; kein aktiver WAF-Service und keine produktive WAF-Konfiguration in `docker-compose.yml`.
    - [x] Fuer die eigenen erstellen Docker-Images wurde ein Sicherheitsscan durchgefuehrt und dokumentiert.
      - Erfuellt: `docs/security-scan.md` und Reports unter `docs/security-scans/`.
    - [x] Der Sicherheitsscan findet keine kritischen Schwachstellen.
      - Erfuellt laut `docs/security-scan.md`: 0 Critical ueber alle eigenen Images.
    - [x] Ein automatisiertes Datenbank-Backup fuer die Datenbank ist eingerichtet.
      - Erfuellt: Service `pg-backup` mit taeglichem Schedule und Volume `legocitytimes-pgbackups`; dokumentiert in `docs/db-backup.md`.
